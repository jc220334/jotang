# 1. 像素是什么？什么是 RGB？灰度图和彩色图有什么区别？

**像素**是数字图片的最小单位，它本身就是一个数字（或一组数字），记录"这一个点有多亮/什么颜色"。
图片在计算机里就是一个数字矩阵，没有别的。本次读到的数组：

```
shape = (332, 591, 3)   dtype = uint8   最小值 = 18   最大值 = 255
```

`dtype=uint8` 表示每个数字占 8 位、取值 0~255：0 表示这一通道完全不发光（最暗），255 表示满亮。

**RGB** 是彩色图记录颜色的方式：每个像素存 3 个数，分别是红(R)、绿(G)、蓝(B)三个通道的强度，
三个数合起来决定这一个点的颜色。例如第 166 行第 295 列那个像素是 `R=122, G=131, B=128`，
三个值很接近且都偏中间，所以那个点看起来是灰蓝色的路面。

**灰度图 vs 彩色图**：

* 彩色图：`(H, W, 3)`，每个像素要 3 个数才说得清颜色。
* 灰度图：`(H, W)`，每个像素只有 1 个数（亮度），没有颜色信息。本图转灰度后 `shape = (332, 591)`。
* 转换公式是加权平均，不是简单取平均：`灰度 = 0.299R + 0.587G + 0.114B`。
  G 的权重最大，因为人眼对绿色最敏感；用这个公式手算，和 `PIL.Image.convert("L")` 的结果最大只差 1
  （四舍五入误差）。
* 反过来，灰度图无法还原成彩色图——颜色信息在转灰度时已经丢了。

# 2. 用 Pillow 读图 → NumPy → PyTorch Tensor，以及 HWC 与 CHW

```python
pil = Image.open(path).convert("RGB")
arr = np.asarray(pil)                 # (H, W, C) = (332, 591, 3) uint8 —— HWC
t = torch.from_numpy(arr.copy())      # 还是 HWC
t_chw = t.permute(2, 0, 1)            # (C, H, W) = (3, 332, 591) —— CHW
t_nchw = t_chw.unsqueeze(0)           # (N, C, H, W) = (1, 3, 332, 591) —— 卷积层要的 4D 形状
```

每个维度的含义（以 HWC 为准）：

| 维度 | 大小 | 含义 |
| --- | --- | --- |
| H（第 0 维） | 332 | 图片有多少**行**（高） |
| W（第 1 维） | 591 | 图片有多少**列**（宽） |
| C（第 2 维） | 3 | 每个像素有几个通道：R、G、B |

取值含义：`arr[y, x]` 是第 y 行第 x 列那个像素的 `[R, G, B]`；`arr.min()=18`、`arr.max()=255`
说明这张图里没有纯黑，但存在纯白（路面的白线）。

**HWC 与 CHW 的区别**（同一块数据，两种摆放顺序）：

* Pillow / OpenCV / matplotlib 习惯 **HWC**：一个像素的三个通道挨在一起，方便"按点取颜色"。
* PyTorch 的卷积层要求 **CHW**（其实还要 batch 维，即 NCHW）：把通道放到最前，
  这样"取出某一个通道的整张图"就是内存里连续的一段，卷积核对每个通道分别做乘加时最省事。
* `permute` 只是换了索引的"视角"，内存没动，所以 `is_contiguous = False`；
  要把它真正喂给 `nn.Conv2d`，最好先 `.contiguous()`（否则会触发隐式拷贝或报错）。
* 转换方式：`arr.transpose(2, 0, 1)`（NumPy）或 `tensor.permute(2, 0, 1)`（PyTorch），
  反向就是 `CHW → HWC`。

# 3. 卷积核是什么？它怎么移动？每到一个位置算什么？

**卷积核**就是一个小矩阵（本实践是 3×3 或 5×5），里面的数字代表"想找的形状"。
它像一个小窗口，从图片左上角开始，**从左到右、从上到下**逐格滑动（每次挪动的格数叫 stride）。

每到一个位置，做三件事：**对齐 → 对应位置相乘 → 全部相加**，得到**一个数**，写进特征图的对应位置。
窗口挪一格，重复一遍。

以程序里实际打印的一处为例（灰度图第 186~188 行、第 124~126 列，正好是黄线上那条竖直边）：

```
窗口 =                     Sobel-X 核 =          对应相乘 =
[[168  93  49]             [[-1  0  1]           [[-168    0   49]
 [184  97  45]              [-2  0  2]            [-368    0   90]
 [150  81  49]]             [-1  0  1]]           [-150    0   49]]

9 个乘积相加 = -498  → 特征图 (186, 124) 这个像素的值就是 -498
```

注意左边三列是亮的路面（168/184/150），右边是暗的（49/45/49）：核里 `-1,-2,-1` 乘左边、
`+1,+2,+1` 乘右边，左右差得越大，结果的绝对值越大。所以这个核的作用就是
**把"左右亮度差"变成输出的大小**——差值越大说明越像一条竖直边。

一句话总结：卷积输出的每个像素，都是"这一小块图像"与"这个核"的**点积**，
衡量的是"像不像"，而不是"有多亮"。

# 4. 只用 Python + NumPy 手写二维卷积

`conv_kernel.py` 里有两个实现，都没用 `cv2.filter2D` / `scipy.signal.convolve2d` / `torch.nn.Conv2d`：

* `conv2d_naive()`：最直白的多重循环——每个输出像素，都把 K×K 个乘积累加一遍。逻辑清楚但慢。
* `conv2d()`：真正使用的版本。外层只遍历核里的 9（或 25）个系数，每个系数一次性把整张图上
  "它负责的那些位置"用切片取出来（形状 `Hout×Wout×C`），乘系数后累加。
  也就是把 **K² 次整图级的乘法** 代替 **每个像素单独算一遍**，全程只有 NumPy 切片和广播。

支持的能力：

| 参数 | 作用 |
| --- | --- |
| `padding=p` | 四周补 p 圈（0 = valid） |
| `stride=s` | 窗口每步滑 s 格 |
| 输入 `(H,W)` 或 `(H,W,C)` | 灰度图和彩色图都能处理（彩色图对每个通道分别卷积） |

**怎么证明写对了**：

1. 手算：上面那个位置算出 -498，程序输出也是 -498。
2. 两个实现互相交叉验证：在 48×48 的小图上分别跑 `conv2d` 和 `conv2d_naive`，
   `padding=1, stride=1` 的最大差异是 `0.00e+00`；`padding=0, stride=2` 也是 `0.00e+00`，
   输出尺寸 `(23, 23)` 与公式一致。两者完全一致，说明实现没问题。

# 5. 四种卷积核处理同一张图片

对比图见 **02_conv_kernels.png**。四种核：

| 核 | 定义 | 结果 |
| --- | --- | --- |
| 3×3 均值模糊 | 9 个元素全是 1/9 | 明显的糊，噪声被抹平 |
| 5×5 高斯模糊 | 按 `exp(-(x^2+y^2)/(2σ^2))` 生成后归一化，σ=1 | 更柔和地糊，没有"方块感" |
| 锐化 | `[[0,-1,0],[-1,5,-1],[0,-1,0]]` | 边缘更硬、对比更强 |
| 边缘检测 | Sobel-X、Sobel-Y，合成 `sqrt(Gx^2+Gy^2)` | 只剩轮廓，路面/天空等平坦区域几乎全黑 |

5×5 高斯核（σ=1，元素之和 = 1.000000）：

```
[[0.003   0.0133  0.0219  0.0133  0.003 ]
 [0.0133  0.0596  0.0983  0.0596  0.0133]
 [0.0219  0.0983  0.1621  0.0983  0.0219]
 [0.0133  0.0596  0.0983  0.0596  0.0133]
 [0.003   0.0133  0.0219  0.0133  0.003 ]]
```

四个结果都用了 same padding（p=1 或 p=2），所以输出尺寸和原图一样是 591×332。

**Sobel-X 和 Sobel-Y 的差别**：Sobel-X 只对左右方向的亮度差敏感，所以输出里亮的是竖直的线
（车道线、柱子）；Sobel-Y 只对上下方向的亮度差敏感，亮的是水平的线（地平线、护栏）。
把两者平方和开根号，就得到"不管哪个方向的边都亮"的合成边缘图，这条路的路沿、车道线、
树冠轮廓全都出来了。

# 6. 为什么会有这些变化？

先给一个定量指标：**高频能量** = 拉普拉斯结果的绝对平均值，数值越大说明细节/边缘越多。

| 图 | 高频能量 | 相对原图 |
| --- | --- | --- |
| 原图 | 4.600 | 100% |
| 3×3 均值模糊 | 2.270 | 49.3% |
| 5×5 高斯模糊 | 1.924 | 41.8% |
| 锐化 | 20.532 | 446.4% |
| Sobel 合成边缘图 | 29.675 | 645% |

**为什么均值/高斯会让图变模糊？**
模糊核里全是正数，而且加起来等于 1，所以输出是"周围一圈像素的加权平均"。
取平均相当于**把邻域的高低起伏抹平**：本来一个像素比邻居亮 50，平均之后只亮一点点，
剧烈的变化（= 高频，= 边缘）被削弱，视觉上就是糊。核越大（5×5 比 3×3）、
参与平均的邻居越多，糊得越厉害。

两者区别在权重：均值核 9 个格子一样重，会有"砖块感"，也更容易在边缘处产生振铃；
高斯核中心权重最大、越靠边越小（中间 0.1621，四角只有 0.003），
相当于离得近的邻居说话更算数，所以过渡更自然、更接近光学镜头的真实模糊。
这也是为什么实际做图像处理时，降噪预处理基本都用高斯而不是均值。

**为什么锐化会让边缘更明显？**
锐化核 `[[0,-1,0],[-1,5,-1],[0,-1,0]]` 可以看成 `原图 + (原图 - 模糊图)`：
中心权重 5、四周 -1（总和 = 1，所以整体亮度不变），等于把"这个像素与邻居的差"放大后加回自己身上。
离边缘越近差异越大，被加得越多，**边缘两侧的对比就被拉开**，所以看起来更"硬"。
指标上高频能量从 4.6 涨到 20.5（446%），正是"高频被放大"的直接证据。

**为什么 Sobel 能找出边缘？**
Sobel-X 是 `[[-1,0,1],[-2,0,2],[-1,0,1]]`：左边一列全负、右边一列全正、中间为 0。
把它盖到图上算点积，等于在算"右边的像素加起来 减 左边的像素加起来"，也就是**左右方向的亮度差**。

* 平坦区域（路面、天空）：左右几乎一样亮 → 正负相消 → 输出接近 0。
* 边缘处（白线、路沿）：左右差很大 → 输出大幅正/负 → 在特征图上亮成一条线。

（Sobel 系数用 1-2-1 而不是三个 1，是为了给靠近中心的像素更大权重，顺便做了一点平滑，
对噪声更稳。梯度有正负号：正表示"从左到右变亮"，负表示"变暗"，看绝对值就知道"这里是不是边"。）

# 7. valid / same、核大小、padding、stride 与输出尺寸

公式（H、W 同理）：

```
H_out = floor((H + 2p - k) / s) + 1
```

在本图（H=332, W=591）上实测，公式和程序输出完全对得上：

| 核 k | padding p | stride s | 公式输出 | 实测输出 | 说明 |
| --- | --- | --- | --- | --- | --- |
| 3 | 0 | 1 | 330×589 | 330×589 | valid，输出比原图小一圈 |
| 3 | 0 | 2 | 165×295 | 165×295 | valid + 降采样 |
| 3 | 1 | 1 | 332×591 | 332×591 | **same，尺寸不变** |
| 3 | 1 | 2 | 166×296 | 166×296 | 尺寸约一半 |
| 3 | 2 | 1 | 334×593 | 334×593 | padding 过大，输出反而变大 |
| 3 | 2 | 2 | 167×297 | 167×297 |  |
| 5 | 0 | 1 | 328×587 | 328×587 | valid，核越大丢得越多 |
| 5 | 0 | 2 | 164×294 | 164×294 |  |
| 5 | 1 | 1 | 330×589 | 330×589 |  |
| 5 | 1 | 2 | 165×295 | 165×295 |  |
| 5 | 2 | 1 | 332×591 | 332×591 | **same，尺寸不变** |
| 5 | 2 | 2 | 166×296 | 166×296 |  |

规律：

1. **核越大，输出越小**。不填充时有效输出边长 = `H - k + 1`，也就是总共少 `k-1` 个像素
   （每边少 `(k-1)/2`：核必须以完整窗口落在图内，中心点没法贴到最外圈）。
2. **padding 是在四周补 0**，每边补 p 圈就让输出边长增加 2p，正好能抵消核造成的缩小。
3. **想保持尺寸不变（same）**：stride=1 时取 `p = (k-1)/2`，即 k=3 用 p=1、k=5 用 p=2。
   这也是 CNN 里 3×3 卷积几乎总配 padding=1 的原因（否则每卷一层图就小一圈，网络没法做深）。
4. **stride 是"每步跳几格"**，输出边长大致变成原来的 1/s，它和池化一样是降采样手段，
   能减少计算量、扩大感受野。
5. padding 过大（比如 k=3 却给 p=2）会让输出比输入还大，一般只在特殊场合才这么干。

**边缘像素的变化**：看图 03 的下面两个放大对比。补 0 的时候，边缘一圈的邻居里混进了 0，
算加权平均就会被"拉暗"，在结果图外边形成一圈灰黑边框（把 p 放大到 10 就看得很清楚）；
如果改成补边缘像素（`np.pad(..., mode="edge")`，也就是重复最外圈的值），
边缘不会有这种突变，所以做卷积时 `edge`/`reflect` 填充通常比 `zero` 更自然。
不过 PyTorch 的 `Conv2d` 默认就是补 0，因为 0 只是"没有信息"，对深层网络影响有限。

# 8. 附：卷积结果越界（<0 或 >255）怎么保存？

锐化结果的范围是 **-85 ~ 638**，其中小于 0 的有 **397** 个像素，大于 255 的有 **4963** 个，
合计约 0.9%。直接 `astype(np.uint8)` 会**回绕**：实测 `[-5.0, -1.0, 300.0] -> [251, 255, 44]`，
负数变成了接近纯白的亮斑——这是很典型的坑（锐化图上莫名其妙的白色噪点就是这么来的）。

三种正确做法（对应图 04）：

| 模式 | 做法 | 适用 |
| --- | --- | --- |
| `clip` | `np.clip(v, 0, 255)` | 如实保存卷积值，负值截到 0。最接近"网络里看到的数" |
| `minmax` | 按实际最小/最大值线性拉伸到 0~255 | 想要对比度最好时用；会改变相对亮度关系 |
| `abs` | 先取绝对值再拉伸 | 边缘图专用——负的边缘和正的边缘一样重要 |

真正训练 CNN 时**不做**这些缩放：数值原样送进网络，由 BatchNorm / ReLU / 权重初始化去处理幅度；
只有把结果导出成图片给人看时，才需要 clip 或归一化。

# 附：这次踩到的两个环境坑（脚本里已修好）

1. **`import torch` 之后一算矩阵乘就崩，没有任何 Python 报错**：
   本环境同时存在两个 OpenMP 运行时——conda 的 mkl 用 LLVM 的 `libomp.dll`，
   torch 自带 Intel 的 `libiomp5md.dll`。torch 先加载了 libiomp5，
   之后 numpy 第一次真正调用 BLAS（`np.dot` / `@`，matplotlib 存图内部也会用）时就会报
   `OMP: Error #15` 并直接中止进程。脚本在最前面设了官方开关
   `KMP_DUPLICATE_LIB_OK=TRUE`（只影响"允许多份 OpenMP 共存"，不改变数值结果；
   卷积算得对不对另有纯 Python 循环实现做交叉验证，不依赖 MKL）。
2. **`torch.from_numpy(PIL 读出来的数组)` 会警告数组只读**：
   PIL 给的数组是只读的，脚本先 `np.array(arr, copy=True)` 复制一份再转 Tensor。
   （另外 `conv_kernel.py` 顶部保留了之前的"环境自举"——把 conda 环境的
   `Library\bin` 加进 DLL 搜索路径，否则会报 `Windows fatal exception: code 0xc06d007f`。）

**先说清楚为什么这套实验能在没有 GPU 的机器上跑完**（本机 torch 2.6.0+cpu，16 核）：

1. 先把 25000 张大小不一的 JPEG 一次性解码、缩放、中心裁剪成 `(24998,128,128,3)` 的 uint8 缓存
   （`data/cache128/images_128.npy`，1.14 GB）。训练时"取一张图"就是一次内存切片，
   不用每个 epoch 重新解码——否则光读图就要两三分钟一轮，还不算和训练线程抢 CPU 的开销。
2. 输入固定 128×128，第一个卷积用 stride=2，比按 224×224 训练省约 3 倍算力。
3. 用 `channels_last` 内存格式（CPU 卷积实测快约 20%）＋ 14 个 torch 线程，
   每轮 85~115 秒。整个实践 2 的实验（6 次训练 + 各种分析）在半小时量级完成。

## 任务 2：数据读取与预处理 —— 怎么组成一个 batch？有没有拉伸/裁剪错误/颜色异常？

代码：`catdog_classifier.py --stages preprocess`，图：**06_preprocess.png**

**预处理流程**（图片从磁盘到网络，一共 8 步）：

```
① JPEG 文件
② PIL.Image.open() 解码
③ .convert("RGB")                      统一成 3 通道，灰度/P/CMYK/RGBA 都在这一步被正确转换
④ 短边等比缩放到 146                   只缩小不放大（小图放大只会变糊）；比例不变 → 不会拉伸
⑤ 中心裁剪 128×128                     把多余边缘切掉；因为比例始终没变，所以物体不会被"压扁"
⑥ 存成 uint8 缓存         (N,128,128,3)          这一步只做一次
⑦ 训练时才做的增强 + float32/255 → (H,W,C) 换轴成 (C,H,W) → 减均值除方差
⑧ DataLoader 把 64 张 (3,128,128) 的图 stack 成 (64,3,128,128) 的 batch
```

**怎么组成一个 batch**：实际取一个 batch 打印出来是这样的——

```
xb.shape = (64, 3, 128, 128)   dtype = torch.float32   # N=64 张，C=3 通道，H=W=128
yb.shape = (64,)               dtype = torch.int64     # 取值 {0,1}，0=猫 1=狗
xb 数值范围 = -1.859 ~ 2.406，均值 ≈ 0.1
```

* **为什么必须统一到 128×128**：`torch.stack` 要求每张图形状一样，原始尺寸差 15625 倍，不可能直接堆；
  而且统一尺寸后卷积核的滑动次数固定，代码和算力都好估计。
* **为什么是 (N,C,H,W) 而不是 (N,H,W,C)**：PyTorch 的卷积层按通道组织数据，
  通道在最前面时，"取出某个通道的整张图"是内存里连续的一段，`Conv2d` 的内核实现最省事；
  这也是任务 1 实践里讲过的 HWC→CHW 转换的用途。
* **为什么 batch 取 64**：太小则每个 batch 的梯度噪声大、并行度低；太大则单批内存和耗时上去、
  而且同样 epoch 数下参数更新次数变少。64 在"CPU 上跑得动"和"梯度够稳"之间比较均衡
  （本轮 17500 张训练图 ÷ 64 = 273 个 batch/epoch）。
* **为什么要减均值除方差**：算训练集统计量得 `mean=[0.478,0.441,0.402]`、`std=[0.257,0.249,0.249]`。
  归一化后输入围绕 0 分布，各通道尺度一致，BatchNorm/Adam 的更新更稳定，收敛更快。
  注意这里的 mean/std **只用训练集算**，不能把验证/测试集的统计量算进去（那属于数据泄漏）。
* **为什么 shuffle=True**：每个 epoch 打乱顺序，避免模型学到"同一类的图总是连着出现"这种顺序信息，
  也让每个 batch 的类别分布更均衡。

**怎么检查没有出错**：图 06 故意挑了三种最容易出问题的图逐列对比——
原图 → 短边缩放后 → 中心裁剪后 → 放大看细节 → 归一化再反归一化。

| 抽查的图 | 原始尺寸 / 模式 | 处理过程 | 结论 |
| --- | --- | --- | --- |
| `Dog/4367.jpg` | 196×33（P 调色板，最"扁"） | 短边缩到 146 → 867×146 → 中心裁 128×128 | 比例没变、没有拉伸；但**两侧被裁掉**，只剩中间一块 |
| `Dog/10749.jpg` | 153×500（RGB，最"瘦"） | 146×477 → 中心裁 128×128 | 主体（狗）仍在，上下内容被裁掉 |
| `Cat/5686.jpg` | 408×277（L 灰度） | 215×146 → 中心裁 128×128 | `convert("RGB")` 之后是正确的中性灰，没有偏色 |

最后"归一化→反归一化"那一列和中心裁剪的结果一致，说明归一化没有丢信息、颜色没有异常。
结论：**几何上只做"等比缩放 + 中心裁剪"，不存在拉伸**（拉伸只会在把图直接 resize 成正方形时发生）；
**颜色上因为显式 `convert("RGB")`，67 张非 RGB 图也不会出错**；
代价是极端长宽比的原图（如 196×33）会被裁掉一部分内容——这是任务 7 里错误样本的一个来源。

## 任务 3：搭建一个包含卷积层、激活函数和池化层的 CNN

代码见 `catdog_classifier.py` 里的 `CatDogCNN`，图：**12_model_arch.png**（任务 9 的结构图也是这张）。

结构是"4 个卷积块 + 一个全连接头"，每个卷积块都是 **卷积层(3×3) → 批归一化 → ReLU → 最大池化**：

| 层 | 类型 | 输入 → 输出 |
| --- | --- | --- |
| features[0] | Conv3×3, stride=2 + BN + ReLU | (3,128,128) → (32,64,64) |
| features[1] | Conv3×3 + BN + ReLU | (32,64,64) → (32,64,64) |
| features[2] | MaxPool 2×2 | (32,64,64) → (32,32,32) |
| features[3] | Conv3×3 + BN + ReLU | (32,32,32) → (64,32,32) |
| features[4] | Conv3×3 + BN + ReLU | (64,32,32) → (64,32,32) |
| features[5] | MaxPool 2×2 | (64,32,32) → (64,16,16) |
| features[6] | Conv3×3 + BN + ReLU | (64,16,16) → (128,16,16) |
| features[7] | Conv3×3 + BN + ReLU | (128,16,16) → (128,16,16) |
| features[8] | MaxPool 2×2 | (128,16,16) → (128,8,8) |
| features[9] | Conv3×3 + BN + ReLU | (128,8,8) → (256,8,8) |
| features[10] | MaxPool 2×2 | (256,8,8) → (256,4,4) |
| head | Flatten → Dropout → Linear(4096,128) → ReLU → Linear(128,2) | (256,4,4) → 2 个 logits |

参数量 **1.108 M**（卷积部分 0.583 M + 全连接头 0.525 M）。

几点设计理由：

* **卷积层**负责在局部找特征：3×3 的核每滑动一处就和那一小块做点积（就是实践 1 里手算过的东西），
  一层一层堆上去，感受野越来越大，特征从"边缘"变成"耳朵/眼睛/毛"再到"整体像不像猫"。
* **激活函数用 ReLU**：`f(x)=max(0,x)`，前向一次比较、反向导数非 0 即 1，没有 Sigmoid/Tanh 的梯度消失问题，
  计算也最便宜。输出层不加激活（直接给 logits），因为配的是 `CrossEntropyLoss`。
* **池化用最大池化 2×2**：每次把特征图边长砍一半，参数量不变但计算量和内存降到 1/4，
  同时让后面卷积的"一个像素"对应原图更大的范围（感受野变大），还带来一点平移不变性
  （物体挪几个像素，池化后的最大值基本不变）。
* **批归一化（BN）**放在卷积和 ReLU 之间：把每层输入重新拉回均值 0、方差 1，
  允许用更大的学习率、对初始化不敏感，也让训练曲线更稳（这也是"改进版"里保留它的原因）。
* **第一个卷积 stride=2**：128×128 原图在 CPU 上算起来最贵，直接用 stride=2 降到 64×64，
  这一层只花约 2% 的算力就省掉后面一半的计算量。
* **倒数第二层用 128 维**再降到 2 类：比直接 Flatten→2 更稳，中间这一层可以当成"图片的向量表示"。

## 任务 4：一张图片经过 CNN 各层后的 Tensor 形状

代码：`--stages arch`（用 forward hook 记录每层输出），图：**07_shapes.png**。
输入 `(1,3,128,128)` 时实测：

| 位置 | 输出形状 | 宽高变化 | 通道变化 | 说明 |
| --- | --- | --- | --- | --- |
| 输入图片 | (1, 3, 128, 128) | — | — | RGB 像素 |
| Conv3×3 s2 | (1, 32, 64, 64) | 128→64（×0.5） | 3→32 | 第一次降采样，通道立刻变多 |
| Conv3×3 | (1, 32, 64, 64) | 不变 | 32 | 通道数由卷积核个数决定 |
| MaxPool2×2 | (1, 32, 32, 32) | 64→32（×0.5） | 不变 | 池化只改空间尺寸 |
| Conv3×3 | (1, 64, 32, 32) | 不变 | 32→64 | |
| Conv3×3 | (1, 64, 32, 32) | 不变 | 64 | |
| MaxPool2×2 | (1, 64, 16, 16) | 32→16 | 不变 | |
| Conv3×3 | (1, 128, 16, 16) | 不变 | 64→128 | |
| Conv3×3 | (1, 128, 16, 16) | 不变 | 128 | |
| MaxPool2×2 | (1, 128, 8, 8) | 16→8 | 不变 | |
| Conv3×3 | (1, 256, 8, 8) | 不变 | 128→256 | 最后一层卷积 |
| MaxPool2×2 | (1, 256, 4, 4) | 8→4 | 不变 | |
| Flatten | (1, 4096) | — | — | 256×4×4 铺平 |
| Linear(4096→128) + ReLU | (1, 128) | | | 图片的 128 维表示 |
| Linear(128→2) | (1, 2) | | | 猫/狗两个 logits |

**规律**：

1. **通道数单调增加：3 → 32 → 32 → 64 → 64 → 128 → 128 → 256 → 256**。
   每过一个"卷积块"，通道翻一倍。可以理解成：网络在路上不断"多开几条检测线"，
   每个通道专门记一种特征（第 5 项的特征图可视化就是看这件事）。
2. **宽高单调减小：128 → 64 → 32 → 16 → 8 → 4**，每次都是池化或 stride=2 卷积砍一半。
   空间分辨率下降到 1/32，但每个位置看到的原图范围（感受野）从 3×3 涨到上百像素。
3. **总信息量**：3×128×128 = 49152 个数 → 256×4×4 = 4096 个数。
   数量少了 12 倍，但语义更强：中间那 4096 个数里装的是"哪里有毛、哪里有耳朵、像猫还是像狗"，
   最后被两个全连接层压成 2 个分数。
4. 图 07 里每一格是"该层所有通道求平均"后的激活图，能直观看到：
   浅层的图还长得像原图（能认出车、狗的形状），越深越抽象，到 4×4 时人眼已经完全看不出图的内容了。

## 任务 6：数据增强的对照实验

### 6.1 哪些变换合理，哪些会破坏标签 / 让图片失真

样例图：**09_augmentation.png**。

| 变换 | 是否合理 | 原因 |
| --- | --- | --- |
| 随机水平翻转 | ✅ 安全 | "猫狗左右翻过来还是猫狗"，标签语义完全不变；同一张图翻转前后是一对天然的成对样本 |
| 随机裁剪 + 缩放（scale 0.5~1.0） | ✅ 基本安全 | 模拟"主体在画面中位置/大小不同"，这正是原始数据集里真实存在的差异；但要控制 scale，见下 |
| 颜色扰动（亮度/对比度/饱和度 ±30%） | ✅ 基本安全 | 模拟不同光照、不同相机的白平衡；猫狗的类别不会因为"偏黄一点"而改变 |
| 裁剪太狠（scale 0.06~0.12） | ❌ 会破坏标签 | 只剩下一块背景或一团毛，画面里可能根本没有猫/狗，标签就错了 |
| 颜色幅度过大（±90%） | ❌ 让图片失真 | 橘猫可能变成蓝猫，已经不像"真实拍摄的照片"，和测试集的分布对不上 |
| 竖直翻转 / 大角度旋转 | ❌ 不建议 | 自然照片里几乎没有倒立的猫狗，这类样本模型在测试时永远遇不到；而且"天空在上"这类先验会被破坏 |

图 09 里第 1~3 行分别是这三种合理增强的不同强度样例，第 4 行是三种"危险做法"的示范。

### 6.2 对照实验怎么做

控制变量：网络结构、优化器（Adam，lr=1e-3，余弦退火）、batch=64、epoch 数、**随机种子全部相同**，
唯一变化的只有"开不开增强"。数据划分是每类各 70%/15%/15%（训练 17498 张 / 验证 3748 张 / 测试 3752 张）。

| 无增强 | **0.8834** |
| 有增强（翻转+裁剪+颜色） | 0.8495 |

| 三者全开 | 0.5000（塌陷） | 模型退化成"永远输出同一类" |

### 6.3 结果说明了一件反直觉的事

**在这次的算力预算下，增强没有让验证准确率变高，反而更低。** 这不是代码写错，可以从曲线和数据看出来：

* 图 10 中间那张 accuracy 曲线：**无增强的模型收敛快得多**（4 轮就到 0.88），
  它的训练曲线（虚线）一路冲到 0.91 以上，验证曲线（实线）开始变平——差距在拉大，也就是开始"背答案"了。
* 有增强的模型每次都"看到不一样的图"，等于每轮要学的任务更难，训练准确率只有 0.81，
  但它的验证曲线**还在往上爬**，训练和验证几乎贴在一起（差距 −0.4 个点）。
* 也就是说：**在这个阶段，过拟合还不是主要瓶颈**，增强"还没轮到发挥作用"，
  它的代价（收敛变慢）却立刻兑现了。颜色扰动最伤（−10 个点）是因为颜色本身是很有用的线索
  （橘猫、黑白花猫这类颜色模式在猫狗之间有统计差异），把它随机化等于把一条有用的线索搅乱了。

**所以"该不该开增强"取决于训练预算**，一般规律是：

1. 训练轮数越少、模型越小、数据越少 → 增强的收益越难体现，甚至有害；
2. 训练轮数足够长、模型容量足够大 → 无增强一定会过拟合，此时增强是性价比最高的手段
   （从上面第二条实验的差距外推：无增强的验证准确率已经停滞，有增强的还在上升，
   如果继续训到 20~30 轮，有增强的版本会追上来——注意这是**外推**，不是实测结果）；
3. 三类变换里，**水平翻转是最安全的**（消融里是唯一带来正收益的），
   裁剪次之（在小预算下会拖慢收敛），颜色扰动要**控制幅度**。

### 6.4 训练配置与耗时（顺便记录）

模型 1.108 M 参数；输入 128×128；Adam(lr=1e-3, weight_decay=1e-4) + 余弦退火；batch=64；
CPU 14 线程、`channels_last` 内存格式；全量训练集 1 轮 85~120 秒（取决于是否开增强），
整个实践 2 一共训练了 10 次（3 次主实验 + 2 次小集对照 + 5 次消融），
加上建缓存和各种分析，总耗时约 55 分钟。

1. **提高输入分辨率**（128→192/224）。错误最集中的"小图/细节不足"一类直接受益；

# 实践 2 · 思考题（课件补充的 6 个问题）

### 思考题 1：卷积层为什么比"一个巨大的全连接层"更适合处理图片？用全连接层实现一遍，对比差距

**怎么做的（真的跑了一遍）**：在脚本里加了 `MLPBaseline`（`--arch mlp`），结构是
`Flatten(3×128×128 = 49152)` → `Linear(49152, hidden)` → `ReLU` → `Linear(hidden, 2)`，
参数量 = 49152 × hidden；用**完全相同的数据划分、优化器、batch、轮数、随机种子**训练，
唯一区别就是"有没有卷积"。结果图：**14_cnn_vs_mlp.png**（`--stages cnnmlp`）。

| 模型 | 参数量 | 轮数 | 学习率 | 最好验证准确率 | 训练准确率 | 每轮耗时 |
| --- | --- | --- | --- | --- | --- | --- |
| **CNN（本任务）** | 1.108 M | 4 | 1e-3 | **0.8834** | 0.8966 | 83 s |
| MLP hidden=22（参数量与 CNN 相当） | 1.081 M | 4 | 1e-3 | 0.6377 | 0.7188 | 14 s |
| MLP hidden=512（"巨大的全连接层"） | 25.167 M | 4 | 1e-3 | 0.6462 | 0.7336 | 52 s |
| MLP hidden=512（调小学习率、训更久） | 25.167 M | 12 | 1e-4 | 0.6633 | **0.9507** | 69 s |
| MLP hidden=22（调小学习率、训更久） | 1.081 M | 12 | 1e-4 | 0.6486 | 0.8443 | 14 s |

**差距有多大**：CNN 用 1.1 M 参数、训练 4 轮就到了 0.8834；而参数多 23 倍的巨型 MLP
训练 12 轮（3 倍训练量、并特意把学习率调小到 1e-4）也只到 0.6633，**差 22 个百分点**。
更刺眼的是图 14 右上那张：MLP 的**训练**准确率已经冲到 0.95，
而**验证**只有 0.66，"训练−验证"差距接近 29 个点——它把训练集背下来了，但完全没有泛化能力。

**为什么差这么多（原理）**：

1. **权重共享 vs 每个位置单独一套参数。** 卷积层一个 3×3 的核只有 27 个权重，
   却要在整张图的每个位置复用（我的第一层 32 个核一共才 864 个参数）；
   全连接层里"左上角的那个像素"和"右下角的那个像素"到同一个隐藏单元是**两条不同的权重**，
   参数量 = 49152 × hidden，25 M 参数里绝大部分在描述"某个固定位置长什么样"，
   而不是"猫长什么样"。
2. **平移等变性 / 不变性。** 卷积 + 池化让"猫挪几个像素、放大一点"得到几乎相同的响应，
   这正是分类任务需要的；全连接层对平移极其敏感：猫在训练集里大多居中，
   测试集里稍微偏一点，输入向量就"面目全非"，而它没有能力把这种变化自动摊平。
   上面 MLP 训练 0.95 / 验证 0.66 的反差就是最直接的证据。
3. **局部性先验。** 图片里"相邻像素才强相关"，卷积只在这个小邻域上做运算；
   全连接层一开始就假设"第 8000 个像素和第 30000 个像素间可能有直接关系"，先验是错的，
   要靠大量数据才能把这层错误结构纠正过来。
4. **层级结构。** 卷积层能一层层把"边缘 → 纹理 → 部件 → 整体"搭起来（见任务 5 的特征图），
   参数效率很高；同样参数量下全连接层只能学到"整张图到类别的加权和"，表达能力差得多
   （hidden=22 的 MLP 与 CNN 参数量相同，结果 0.638 vs 0.883）。
5. **附带一个实操坑（也是"巨型全连接层不好训"的体现）**：第一层的 fan_in = 49152，
   用默认的 lr=1e-3 时 Adam 每步对每个权重的移动量相对初始权重量级过大，
   训练第 1 轮平均 loss 会先冲到 2.13（正常应在 0.7 左右）再回落；把学习率降到 1e-4 才稳定。

**但也要说清楚一点**：MLP 的问题**不是算不动**。它每张图的乘加次数只有约 25 M，
比 CNN 的约 173 M 还小 7 倍，所以每轮反而更快（14~69 s vs 83 s）。
卷积的优势不是"省算力"，而是**在同样的数据量和训练预算下能学到更通用、更平移不变的表示**——
也就是"数据效率"和"泛化能力"，这才是处理图片时决定性的东西。

### 思考题 2：卷积层的输入通道和输出通道分别表示什么？它们与卷积核的数量有什么关系？

* **输入通道 = 上一层交给这一层的"信号种类"**。对第一层来说就是图片的颜色通道（R、G、B 三个），
  我的网络里 `features[0]` 的 `in_channels=3`；对后面的层来说，输入通道就是上一层输出的特征图张数，
  比如 `features[3]` 的 `in_channels=32`，对应上一层那 32 个卷积核产生的 32 张特征图。
* **输出通道 = 这一层"想找的特征种类"数 = 卷积核的个数**。每个卷积核负责产生**一张**输出特征图：
  卷积核在输入上滑动，每到一个位置就把"所有输入通道"对应位置的值加权求和（再叠加），
  得到输出特征图上的一个数。所以：

  ```
  输出通道数 C_out  ==  卷积核的个数
  每个卷积核的形状  ==  (C_in, k, k)   ← 深度必须等于输入通道数，由框架自动匹配
  参数量            ==  C_out × C_in × k × k   （bias=False，偏置交给 BatchNorm）
  ```

  本网络里三处的实际数字：

| 层 | 通道变化 | 卷积核个数 | 每个核的形状 | 权重数量 |
| --- | --- | --- | --- | --- |
| features[0] | 3 → 32 | 32 | 3×3×3 | 32×27 = 864 |
| features[3] | 32 → 64 | 64 | 3×3×32 | 64×288 = 18432 |
| features[9] | 128 → 256 | 256 | 3×3×128 | 256×1152 = 294912 |

* 两个容易混的点：
  1. **"输入通道数"不是超参数**，它由上层的输出决定；**能够自己选的只有输出通道数（= 卷积核个数）**。
  2. 一个卷积核**跨通道求和**，把 C_in 张输入图压成 1 张输出图；想要输出 32 张图就得有 32 个不同的核。
     "输入通道 3、输出通道 32" 的意思就是"用 32 个不同的小模板去扫描这张彩色图，每个模板产出一张特征图"。
* 顺带对比：全连接层里没有"通道"这个概念，每个隐藏单元都和**所有**输入相连（49152 条权重）；
  卷积层则是"局部连接 + 通道内共享权重"，这正是它参数少的原因（864 个参数就能在 64×64 的图上工作）。

### 思考题 3：padding、stride 和 pooling 怎样改变特征图尺寸？结合本网络的一层实际计算

公式（与实践 1 任务 7 推导的一致）：

```
H_out = floor((H_in + 2p - k) / s) + 1        （宽 W 同理）
```

拿我自己网络里的层逐条代入（H_in 以高为例，实测值来自 `--stages arch` 打印的形状表）：

| 层 | 配置 | 代入计算 | 输出 | 实测 |
| --- | --- | --- | --- | --- |
| features[0] | Conv3×3, **p=1, s=2** | floor((128 + 2 − 3)/2) + 1 = floor(127/2) + 1 = 63 + 1 | 64 | 64 ✔ |
| features[1] | Conv3×3, p=1, s=1 | floor((64 + 2 − 3)/1) + 1 = 63 + 1 | 64 | 64 ✔（same，尺寸不变） |
| features[2] | MaxPool 2×2, s=2 | floor((64 − 2)/2) + 1 = 31 + 1 | 32 | 32 ✔ |
| features[3] | Conv3×3, p=1, s=1 | floor((32 + 2 − 3)/1) + 1 | 32 | 32 ✔ |
| features[5] | MaxPool 2×2 | 32 → 16 | 16 | 16 ✔ |
| features[8] | MaxPool 2×2 | 16 → 8 | 8 | 8 ✔ |
| features[10] | MaxPool 2×2 | 8 → 4 | 4 | 4 ✔ |

三个因素各自的作用：

* **padding（p）**：在四周补 0，把"卷积核中心"推到边界外的位置，让边上的像素也能被完整覆盖。
  stride=1 时输出边长增加 2p，所以想让尺寸不变（same）就取 `p = (k-1)/2`：k=3 用 p=1（features[1] 就是），
  k=5 用 p=2。如果不补 0，每卷一层图就小一圈（128 → 126），网络根本没法做深。
* **stride（s）**：窗口每次挪 s 格，输出边长大约变成 1/s，它把"降采样"和"卷积"合并成一步。
  我在 features[0] 就用了 s=2，让 128 直接变 64——这一步只花约 2% 的算力，却省掉后面一半的计算量；
  注意 s>1 时 `p=(k-1)/2` 不再保证 same，实际是"输出 ≈ 输入的一半"（128 → 64），这既是设计，也是我想要的。
* **pooling**：独立的降采样层，2×2 最大池化把边长减半、参数量为 0（没有可学参数），
  和 stride=2 卷积相比它更"机械"：只做局部取最大值，不引入新参数。
  代价是丢掉四分之三的位置信息，但留下的"最大值"能说明"这附近有没有这种特征"。
* 合起来看整条链：**128 →(s=2 卷积) 64 →(池化) 32 →(池化) 16 →(池化) 8 →(池化) 4**，
  空间尺寸缩到 1/32；通道数 3 → 32 → 64 → 128 → 256 涨到 85 倍。两者一涨一缩，正好是思考题 4 的内容。

### 思考题 4：为什么特征图的宽高越来越小，通道数却越来越多？

1. **分类任务只需要"是什么"，不需要"在哪里"。** 池化和 stride 主动丢掉精确位置，
   换来对"物体稍微挪动/缩放"的容忍度（局部平移不变性）——这恰恰是猫狗分类想要的：
   猫在左上角还是右下角都该被判成猫。如果一直保留高分辨率，模型会把大量容量花在"记住位置"上。
2. **算力守恒：这是最现实的原因。** 卷积的计算量 ≈ `H×W×C_in×C_out`。
   如果宽高不降、只想加通道，代价是平方级上涨：在 128×128 上做一次 256 通道的 3×3 卷积，
   是 8×8 上同样运算的 256 倍。所以"降空间 + 升通道"是让算力可承受的常规做法。
3. **信息形态从"空间细节"迁移到"语义组合"。** 浅层要保留细小结构才能发现边缘/颜色/纹理，
   所以分辨率高、通道少；越深，单个位置已经"看到"了很大一片区域（感受野变大），
   它需要表达的是"这里有没有耳朵/胡须/花纹"这类语义证据，而**每多一种证据就需要一个通道去记**，
   于是通道数越堆越多。这也解释了为什么最后一层 256 个通道在 8×8 上：每个位置都在回答"这一带像不像猫/狗"。
4. **感受野与位置精度的权衡。** 每经过一次池化/stride，后面像素的感受野大约翻倍，
   位置精度自然越来越粗；既然精度已经不重要，把剩余的表达能力放到"通道"（特征种类）上更划算。
5. **附带的好处是压缩与正则化。** 我的网络从 `3×128×128 = 49152` 个数压到 `256×4×4 = 4096` 个数
   （总元素降到 1/12），信息被"压缩 + 抽象"了一遍；这种压缩也让后面的全连接层参数不至于爆炸
   （如果保持 128×128×256 = 4.2 M 维，一层全连接就有 4.2M × hidden 个参数，根本接不动）。

### 思考题 5：你选择了什么激活函数和损失函数？它们为什么适合这道二分类题？

**激活函数：ReLU（`f(x) = max(0, x)`）**，放在每个卷积层（和 BatchNorm）之后、以及全连接层之后（输出层不加）。

* 导数只有 0 和 1 两种取值，**没有 Sigmoid/Tanh 那种"两端饱和"的区域**，
  梯度不会被压扁，所以层层堆叠也能训练得动（这是它取代 Sigmoid 的根本原因）。
* 前向只做一次比较、反向一次判断，**计算最便宜**；负半轴输出恒 0，还有一点"稀疏激活"的效果。
* 它是非线性的，卷积 + ReLU 的组合才能表达"边缘→纹理→部件"这种复杂的非线性特征；
  如果只有卷积（线性），多少层叠起来都等价于一层线性变换。
* 已知的坑：可能出现"神经元死亡"（某单元恒输出 0、梯度恒为 0）。真遇上可以换 LeakyReLU / GELU；
  本网络加了 BatchNorm，输入分布比较稳定，训练中没有观察到明显死亡。

**损失函数：交叉熵 `CrossEntropyLoss`（配合"2 个 logits"的输出层）。**

* 二分类本质上是"在 2 个互斥类别上给出一个概率分布"，而交叉熵 `L = −Σ y·log p`
  正好衡量"预测分布"和"one-hot 真值"之间的差距，是分类任务的标准选择（本质上是最大似然）。
* **网络输出层不加 softmax，直接输出 logits**，`CrossEntropyLoss` 内部做 `LogSoftmax + NLLLoss`。
  这样做数值上更稳（避免概率接近 0 时的 `log(0)` 和指数上溢），损失对 logits 的梯度也干净漂亮：
  `∂L/∂z = p − y`（预测概率减真值），和 Adam/SGD 配合很好。
* **为什么不用"1 个输出 + BCEWithLogitsLoss"**：那样也可以（二分类的特例），
  但用"2 个 logits + CE"能让二分类和多分类代码**完全统一**——以后改成三分类只需把
  `Linear(128, 2)` 改成 `Linear(128, 3)`，损失函数和训练循环一行都不用动（实践 1 的问答里也是这个结论）。
* 怎么算才合适还看数据：本数据集两类各 12499 张、完全均衡，所以直接用**准确率**做评价指标就够了
  （如果类别极不平衡，就该看混淆矩阵、召回率/精确率，甚至换 focal loss）。
* 改进版里额外开了 `label_smoothing=0.05`：把"硬标签"0/1 变成 0.025/0.975，
  防止模型对训练样本过度自信（对噪声标签更宽容）。实测它没能在这个预算下提升准确率（见任务 6/7），
  但训练过程的"自信程度"确实更温和，这个技巧在大数据集上通常是有益的。

### 思考题 6：为什么训练集的随机增强不能原样用到验证集和测试集？三种变换各有什么帮助与问题？

**先说为什么不能。**

1. **验证/测试集的唯一职责是"估计真实泛化误差"，所以它必须代表真实分布。**
   训练时做随机增强，是我们主动去"制造更多更难的变化"来提升泛化能力；
   如果把同样的随机扭曲加到验证/测试集上，量到的就是"模型在被人为改造过的数据上的表现"，
   既不是真实水平，也没法和其他人/别的模型比较（相当于把考卷换成了另一套题）。
2. **随机性会破坏可复现性和可比性。** 同一张图每次评估都被随机改变（随机裁剪的位置、随机的颜色系数），
   同一个模型的准确率每次评估都会抖动；两个模型之间的差距可能被这点噪声直接淹没。
   评估必须**确定性**：我这里的做法是缓存里只保留"等比缩放 + 中心裁剪"这种确定性预处理，
   训练/验证/测试三者共用同一套，只有训练时才额外叠加随机增强。
3. **两者想要的东西正好相反**：训练集要"尽量多样"，验证/测试集要"保持原样、暴露模型没见过的情况"。
   把验证集也随机化，等于把"考试题"提前变成"练习题的另一种形态"，会系统性高估或低估模型的真实能力。
4. **例外：TTA（Test-Time Augmentation）是可以的**，因为它不是随机的——
   对每张测试图做**固定的一组**变换（这里只有水平翻转），各自预测后取平均，结果是确定性的，
   目的是降低单次预测的方差。本任务实测有效：无增强模型测试集准确率 0.8857 → 0.8982（+1.25 个点），
   改进版 0.8689 → 0.8718。**"固定变换 + 平均"可以用于推理，"随机变换"只用于训练**，这就是分界线。

**三种变换的帮助与问题**（样例见 `09_augmentation.png`，实验数字见任务 6）：

| 变换 | 带来的帮助 | 可能的问题 |
| --- | --- | --- |
| 随机水平翻转 | 免费把数据量翻倍；告诉模型"猫狗左右对称"，不再依赖左右朝向；代价最小、最安全（消融里是唯一正收益：0.7500 → 0.7695） | 如果类别与方向有关就会出错（文字、交通标志、左右手/左右耳的区分）；猫狗不存在这个问题，所以本任务里安全 |
| 随机裁剪 + 缩放 | 让模型不依赖"主体总在正中央、总是同样大小"，模拟真实拍摄的构图差异；对"人+动物""背景草地"这类伪相关也有一定抑制作用 | 裁得太狠（scale 0.06~0.12）只剩一团毛或一块背景，**标签就不成立了**；另外它会明显拖慢收敛（消融 4 轮：0.7500 → 0.7335） |
| 颜色扰动 | 让模型别过度依赖颜色（不同光照/白平衡/相机的差异），削弱"橘猫=猫"这种捷径；对真实照片的亮度变化更鲁棒 | 猫狗之间颜色本身存在统计差异（橘猫、黑白花猫），幅度太大等于把有用线索随机化；±30% 还算自然，±90% 图片就明显失真了。消融里它最"伤"（4 轮：0.7500 → 0.6500） |
| （对比）竖直翻转 / 大角度旋转 | 如果真实数据真有这种视角，可以打开 | 自然照片里几乎不会出现倒立的猫狗，等于逼模型学"永远遇不到"的样本，还会破坏"天空在上"这种先验，所以本任务不使用 |

最后结合前面的实验给一个结论：增强的本质是**用"收敛速度"换"泛化上限"**。
在我的训练预算里（4~8 轮）它甚至让验证准确率变低，但它把过拟合差距压小了很多
（6000 张训练集、8 轮：无增强的"训练−验证"差距 +5.8 个点，有增强只有 −0.4 个点）；
数据越少、训练越久、模型越大，这笔交易就越划算。
